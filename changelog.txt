= Changelog =

== 1.4.3 – 2026-07-21 ==
* Fixed (critical): init() never ran on v1.3.2–1.4.2. The class-redeclaration backstop added in 1.3.2 was a plain `if (class_exists('Update_Logger')) return;` at the top of the file, but PHP hoists unconditional top-level class declarations at compile time — so the class always existed by the time the guard ran, the file returned early, and Update_Logger::init() was never called (no hooks, no REST endpoint, no mirror refresh). The guard now wraps the whole class + init() call in `if (! class_exists('Update_Logger')) : ... endif;`, which both prevents compile-time hoisting (so init runs) and still guards against a genuine double-load. Verified: single load registers all 17 hooks incl. rest_api_init; double load does not fatal

== 1.4.2 – 2026-07-21 ==
* Added: Read-only REST endpoint GET /wp-json/znackarna/v1/status returning the auto-update config, recent update history and an uploads-writability diagnostic. This is a robust transport for the web-audit connector: it is not page-cached, needs no uploads write and no FTP path guessing, and works on sites without an application password. Entry collection refactored into a shared collect_entries() (SELECT * + suppressed errors, schema-drift safe). The connector prefers this endpoint and falls back to the FTP JSON mirror

== 1.4.1 – 2026-07-21 ==
* Fixed: The JSON mirror now always writes the "config" block (auto-update state) even when the update_log query fails — e.g. a site that ran an older standalone version left a table with a different schema, so `SELECT ... method ...` errored and the whole mirror write bailed, leaving the connector with no data. The query is now `SELECT *` with suppressed errors and null-coalesced columns, config is built independently of the table, and file_put_contents no longer uses LOCK_EX (better cross-host compatibility)

== 1.4.0 – 2026-07-21 ==
* Changed: Renamed to "Správa značkárny" (Author: značkárna s.r.o.) with a descriptive header, so the must-use bootstrap wrapper and the plugin list show a meaningful name instead of the bare filename. Admin log page menu label follows. Internal slugs, text domain and the update_log DB table are unchanged — no data or behaviour impact, only the display identity

== 1.3.2 – 2026-07-21 ==
* Fixed: Guard against a fatal class redeclaration when the plugin is present both as a must-use plugin (connector-deployed) and as a regular plugin. A `class_exists('Update_Logger')` backstop at the top of the file returns early instead of declaring the class twice. The primary protection lives in the connector's mu bootstrap wrapper (it does not load the mu copy when a standalone update-logger / wordpress-update-logger plugin exists in plugins/); this is the second line of defence. Prevents the HTTP 500 seen when a site already ran the standalone plugin

== 1.3.1 – 2026-07-21 ==
* Added: Self-healing mirror refresh. A new maybe_refresh_mirror() runs on 'init' (priority 20) and rewrites uploads/znackarna/update-log.json whenever it is missing, the plugin VERSION changed (i.e. the connector just deployed a new build), or the file is older than 6 hours. This keeps the "config" block (auto-update state, which can change any time an admin toggles a plugin's auto-update) fresh without relying on wp-cron — each daily connector REST pass fires 'init' and regenerates the mirror before it is read over FTP. Table creation no longer writes the mirror itself (moved to the refresh path). New VERSION constant kept in sync with the plugin header
* Note: The actual file write still runs rarely (guarded by mtime + version), so the per-request cost is just a filemtime() check

== 1.3.0 – 2026-07-21 ==
* Added: The JSON mirror now includes a "config" object with the current auto-update STATE — core level (off/minor/major, mirroring WP core's WP_AUTO_UPDATE_CORE / auto_update_core_major logic), pluginsAuto/pluginsTotal, themesAuto/themesTotal, per-plugin auto flags, and the updaterDisabled/fileModsDisabled blockers. WordPress core does not expose per-plugin auto-update state over REST (/wp/v2/plugins has no auto_update field), so the značkárna web-audit connector — which has no WP-CLI/DB access — reads it here instead. Source of truth: get_site_option('auto_update_plugins'/'auto_update_themes'), the WP_AUTO_UPDATE_CORE constant and auto_update_core_major option
* Note: config is recomputed on every mirror write (each logged update + once on table creation), so the connector always sees the live auto-update configuration

== 1.2.3 – 2026-07-21 ==
* Changed: Table creation and JSON-mirror materialization now hook 'init' instead of only 'admin_init', so a freshly connector-deployed must-use plugin writes its uploads/znackarna/update-log.json on the first front-end or REST request — no wp-admin visit required. Still guarded by get_site_option, so dbDelta runs only once. This lets the web-audit connector see updateHistory.available flip to true on its next inventory pass rather than waiting for someone to log into wp-admin

== 1.2.2 – 2026-07-21 ==
* Added: Must-use plugin mode. When the file lives directly in WPMU_PLUGIN_DIR (the značkárna web-audit connector deploys it there over FTP — no activation, connector-managed updates), the GitHub self-updater is skipped so it does not inject a phantom "update available" for a plugin WordPress has no entry for. As a normal plugin the self-updater behaves exactly as before. Table creation, logging, admin log page and the JSON mirror all work in both modes

== 1.2.1 – 2026-07-21 ==
* Added: JSON mirror of the update log at wp-content/uploads/znackarna/update-log.json (path via wp_upload_dir(), so it respects WP_CONTENT_FOLDERNAME like "files"). Written after every insert_row and once on table (re)creation. Contains the last 50 events with no PII (at/type/slug/from/to/status/method) so the značkárna web-audit connector — which has no WP-CLI/DB access, only FTP/REST — can read the real update history and surface it in the CRM (updateHistory block of web-audit/report@1)
* Note: The mirror is additive and fails silently; it does not change the update_log table or any existing behaviour

== 1.2.0 – 2026-05-14 ==
* Added: Self-update from GitHub releases. The plugin polls api.github.com/repos/znackarna/wordpress-update-logger/releases/latest once per 12 h and injects the latest tag into the WordPress update transient, so new versions appear in the standard "Plugins → Updates available" UI without any external library
* Added: register_update_checker() wires three filters (pre_set_site_transient_update_plugins, plugins_api, upgrader_source_selection) and a 12-hour cached fetch_latest_release() helper. The upgrader_source_selection hook renames GitHub's zipball folder (znackarna-wordpress-update-logger-&lt;sha&gt;) to the canonical wordpress-update-logger slug so the plugin path survives the update
* Note: Updates are driven by GitHub releases — without a published release (gh release create vX.Y.Z) no site sees the update. Header version must match the release tag (Version: X.Y.Z in plugin header, tag vX.Y.Z on GitHub)

== 1.1.9 – 2026-04-30 ==
* Removed: Diagnostic ring buffer (HOOK_LOG_KEY site option, record_hook_fire helper, admin notice block, ul_clear_hook_log handler). The redundant upgrader_overwrote_package hook from 1.1.8 verifiably catches ZIP-upload reinstalls in production, so the temporary debug surface is no longer needed
* Improved: on_manual_update install branch derives the plugin/theme from $upgrader->result['destination_name'] via a new resolver against the canonical full get_plugins() / wp_get_themes() catalog, falling back to $upgrader->plugin_info() / theme_info() only on miss. Avoids the cache/timing artifact where plugin_info() returned empty inside the upgrader_process_complete callback and the row had to rely entirely on the redundant hook
* Note: The 1.1.8 site option update_logger_hook_log is now orphaned. It is a tiny ring buffer (<2 KB) and will be left untouched; admins can delete it manually via the network options table if they care

== 1.1.8 – 2026-04-30 ==
* Added: Hook into upgrader_overwrote_package as a canonical fallback for ZIP-upload reinstalls (fires from Plugin_Upgrader::install() / Theme_Upgrader::install() after a successful overwrite). Plugin/theme is resolved by matching new metadata against the installed catalog
* Added: Per-request deduplication in insert_row to prevent duplicate rows when both upgrader_process_complete and upgrader_overwrote_package fire for the same overwrite
* Added: Temporary diagnostic ring buffer (last 10 upgrader hook fires, displayed as a notice on the admin log page with a Clear action). Captured before any guard so the admin can confirm whether the hook reaches the plugin at all. To be removed once the upload-overwrite logging path is verified across the affected hosting setups

== 1.1.7 – 2026-04-30 ==
* Fixed: ZIP-upload reinstalls (Plugins → Add New → Upload Plugin → Replace current with uploaded) are now logged. The previous overwrite check relied on a $hook_extra['overwrite'] key that WordPress never sets; the upgrader's clear_destination flag is checked instead, and the affected plugin/theme is derived from $upgrader->plugin_info() / theme_info() since action=install does not populate plugins/themes in $hook_extra
* Improved: Plugin/theme slug for upload-overwrite installs is resolved via the upgrader, so old/new versions are recorded the same way as for regular updates
